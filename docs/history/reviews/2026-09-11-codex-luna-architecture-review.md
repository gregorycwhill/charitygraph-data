Evidence labels used below:

- **[OBSERVED]** directly inspected code, tests, configuration or Git history.
- **[DOCUMENTED]** stated in project documentation.
- **[REPORTED RUNTIME]** aggregate runtime evidence documented by the project but not independently reproducible from public Git.

## 2. Executive judgement

CharityGraph has a coherent and unusually serious thesis: create an open, evidence-linked, contestable Australian charity knowledge layer that is more useful than a directory while avoiding universal charity rankings or opaque recommendation logic.

The strongest part of the project is its epistemic and lineage discipline. The Builder code distinguishes source records, artefacts, evidence locators, tasks, attempts, model results, observations, assertions, decisions and projections. The Data repository explicitly treats releases as immutable projections rather than mutable truth tables. Viewer and Playbooks have clear non-recommendation and non-hosted-inference boundaries.

The main concern is not that the architecture is fundamentally misguided. It is that the implementation has accumulated a substantial control-plane and experiment-management system before the public product has demonstrated equivalent user value. The codebase is already broad, with more than one hundred source and test files in the Builder snapshot, multiple historical and experimental paths, provider-specific transport logic, durable mandate machinery, SQLite orchestration, and several evolving semantic contracts.

The pinned Builder snapshot also does not pass its complete test suite: four failures remain, including a production-contract prompt-policy mismatch and a stale registry-count expectation. That is a material release-readiness issue.

Overall judgement:

> CharityGraph is directionally sound and technically credible as an evidence-governed data product, but it is not yet production-complete. The next priority should be reducing implementation uncertainty and proving useful public workflows, not adding more semantic domains or expanding the control plane.

## 3. What CharityGraph is

### Product problem

**[DOCUMENTED]** Charity information is distributed across regulators, annual reports, websites, financial filings, service directories, research, government material and other public sources. CharityGraph aims to reduce the cost of locating, joining, interpreting and comparing that information.

Its intended output is not merely a directory entry. It is a structured, source-aware representation of:

- legal and operating identities;
- programs and services;
- populations and geography;
- participation;
- fundraising and finances;
- governance and workforce;
- relationships and ecosystem context;
- commitments, conduct and notable history;
- evidence, uncertainty and coverage.

### Users

The principal user appears to be an analyst or consultant, with secondary users including:

- funders and service planners;
- researchers and journalists;
- charity staff and contributors;
- software developers and data analysts;
- downstream AI systems;
- ordinary public users seeking inspection and discovery;
- decision-makers using Playbooks for structured analysis.

### Product family

The repositories establish four distinct products:

```text
Builder
  acquires and processes source material
  constructs governed knowledge and release candidates

Data
  publishes reusable governed data
  maintains shared product and public-contract authority

Viewer
  provides public inspection, search, navigation and correction entry points

Playbooks
  publishes reusable analytical methods for use with a user's chosen AI
```

This separation is sound in principle. It prevents the Viewer becoming a second database and prevents Playbooks becoming a hosted inference product.

### Differentiation

CharityGraph is differentiated from:

- a conventional directory, through program/service and evidence granularity;
- a search product, through structured source-linked claims and projections;
- a knowledge graph, through explicit provenance, scope, uncertainty and publication governance;
- an analytics platform, through its public governed-data orientation;
- a recommendation engine, through its explicit rejection of universal desirability rankings.

The differentiation is meaningful, but not yet fully proven in public usage.

## 4. Product thesis assessment

The thesis is:

- **coherent:** yes;
- **useful:** plausibly, especially for analysts and service planners;
- **differentiated:** yes, if evidence and contestability survive scale;
- **technically achievable:** yes, at bounded scale;
- **appropriately ambitious:** only if staged aggressively;
- **currently over-broad:** yes.

The product attempts to cover a large number of claim families and source classes while also supporting semantic extraction, multiple taxonomies, graph relationships, corrections, Playbooks, public releases and AI-oriented distribution.

The core value proposition should be narrowed operationally to:

> Find and inspect evidence-backed organisations, programs, services and relationships, with scope, source role, uncertainty and coverage visible.

That is already a compelling product. The remaining domains should be justified against concrete user workflows rather than treated as an equal-priority completeness target.

## 5. Product design and domain model

### Essential concepts

These abstractions appear essential:

- opaque subject identity;
- scoped entities;
- source records;
- immutable artefacts;
- evidence locators;
- source authority and role;
- observations versus assertions;
- task and result identity;
- explicit missingness;
- governed decisions;
- immutable release projections;
- correction lineage.

They are not merely academic distinctions. They prevent common failures such as:

- treating a charity's legal purpose as proof of current activity;
- treating a regulator record as a service description;
- propagating partner facts to the charity;
- treating a model output as canonical knowledge;
- overwriting historical evidence with a newer interpretation.

### Useful but premature concepts

These are valuable but probably premature for the current product stage:

- full multi-domain relationship semantics;
- broad fundraising mechanism modelling;
- exhaustive workforce and capability detail;
- generalized model-routing economics;
- multiple semantic contract families before the first public vNext;
- Playbook ecosystem workflows;
- broad corpus-scale technical replication.

They should remain designed, but not necessarily implemented before the core program/service and evidence experience is demonstrably useful.

### Potentially over-modelled areas

The internal model contains a large number of lifecycle and domain distinctions. That is justified for Builder internals, but the project risks exposing them too early through public contracts and downstream clients.

The Data documents correctly state that cards are projections, not the source of truth. The practical danger is that too many public-facing projections may reproduce internal complexity instead of presenting a useful hierarchy.

A good principle is:

```text
rich internal semantics
        ↓
small stable public primitives
        ↓
progressive disclosure in Viewer and APIs
```

## 6. Epistemic and editorial model

This is CharityGraph's strongest conceptual area.

The project explicitly distinguishes:

- regulator facts;
- accounting facts;
- first-party claims;
- independent observations;
- source-native records;
- derived mappings;
- model candidates;
- governed assertions;
- adjudication;
- public projections.

The Data governance chain is explicit:

```text
source registry
  → acquisition event
  → source artefact
  → evidence span or source-native record
  → observation
  → assertion/classification
  → adjudication
  → publication projection
  → release
```

That is materially stronger than the common pattern of storing one mutable summary field per charity.

### Missingness

The explicit distinction between:

- not acquired;
- unavailable;
- failed;
- not found;
- source silent;
- insufficient evidence;
- unknown;
- not applicable;
- withheld;
- stale;

is excellent. Missing data must not acquire negative meaning, especially for smaller, local, culturally specific or lightly documented charities.

### Scope

The rules that program and service evidence should remain at the lowest supported scope are also strong. The system should not infer organisation-level claims merely because a program belongs to that organisation.

### Neutrality

The neutrality policy is defensible as a product boundary but cannot be guaranteed solely by schema design.

Downstream users can:

- rank charities;
- construct proprietary scores;
- select evidence selectively;
- use public data for commercial targeting;
- combine CharityGraph with biased external datasets.

CharityGraph can control its own published projections and explain its methods. It cannot control all downstream use.

Its defensible position is therefore not “the data cannot be used for ranking.” It is:

> CharityGraph does not itself publish universal desirability rankings and preserves the evidence, scope, source role and uncertainty needed for users to understand what a downstream ranking means.

## 7. Epistemic implementation gap

The implementation generally supports the documented model, but the gap is substantial in three areas.

### First: model outputs are structurally governed, not semantically proven

The code can validate:

- schema shape;
- evidence-reference membership;
- known identifiers;
- contract identity;
- lifecycle state;
- provider and usage metadata.

It cannot mechanically establish that a proposal is substantively correct. That requires evaluation and review.

### Second: public releases do not expose the full private lineage

The private runtime and raw evidence are deliberately excluded from Git. This is appropriate for privacy, rights and operational safety, but it means many important claims are not independently reproducible from the public snapshot.

### Third: semantic quality remains weakly measured

The current evaluation design discusses useful metrics such as:

- evidence support;
- subject-set overlap;
- granularity stability;
- operational-status agreement;
- proposal-count dispersion;
- semantic repeatability.

However, the public snapshot does not establish a mature gold-standard quality score for these dimensions.

## 8. Actual architecture

The implemented architecture is broadly:

```text
governed source universe
        ↓
source definitions and acquisition receipts
        ↓
retained content-addressed artefacts
        ↓
source-native records and representations
        ↓
subject/scope binding
        ↓
evidence locators
        ↓
execution packet construction
        ↓
semantic contract resolution
        ↓
provider request compilation
        ↓
delivery transport
        ↓
receipts, usage and raw results
        ↓
schema/evidence validation
        ↓
candidate knowledge
        ↓
governed observations/assertions/decisions
        ↓
private projections
        ↓
immutable Data release
        ↓
Viewer and Playbooks
```

### Repository boundaries

The separation is clear:

- Builder owns acquisition, runtime control, evidence and semantic execution.
- Data owns public contracts, documentation, releases and shared authority.
- Viewer consumes data and provides inspection.
- Playbooks defines methods and portable invocations.

The boundary is weakened slightly by historical naming and compatibility material, especially legacy CauseBase identifiers and modules.

### Control plane

The Builder SQLite catalogue stores:

- cohorts;
- runs;
- tasks;
- attempts;
- leases;
- reservations;
- cost entries;
- artefact metadata;
- source definitions;
- acquisition receipts;
- evidence locators;
- provider request items;
- delivery jobs;
- execution mandates;
- semantic authorizations.

This is a serious control plane for a local execution system.

### Data plane

Evidence bodies and derived representations live outside SQLite in content-addressed filesystem storage. SQLite stores identifiers, hashes and operational metadata rather than full source bodies.

That is a sensible local architecture.

### SQLite assessment

SQLite is appropriate for:

- local bounded execution;
- append-only records;
- deterministic replay;
- experiment coordination;
- a single operator or small number of workers.

It will become a bottleneck for:

- distributed workers;
- large concurrent campaigns;
- hosted multi-tenant operations;
- high-volume reconciliation;
- globally coordinated queues.

The project does not need to replace SQLite now. It should, however, preserve a clean repository/service abstraction so migration is possible without changing semantic contracts.

## 9. Identity, hashes and immutability

The identity design is strong.

The code distinguishes:

- logical task IDs;
- model-task IDs;
- provider request-item IDs;
- delivery-job IDs;
- physical attempts;
- provider request IDs;
- provider receipt IDs;
- raw-result references;
- content hashes;
- schema hashes;
- semantic contract hashes;
- provider-wire fingerprints.

The provider request identity correction was particularly principled: identity is derived from provider-significant stable material before ephemeral attempt fields are injected.

This prevents a corrected request from accidentally reusing an earlier terminal request row.

### Limitation

Hashes provide integrity and deterministic identity, not authenticity. A hash proves that bytes correspond to a claimed digest; it does not prove who created or authorized them.

For higher-assurance publication or provider authorization, signed manifests or equivalent authenticated attestations will eventually be necessary.

## 10. Evidence and provenance implementation

The [execution packet code](https://github.com/gregorycwhill/charitygraph/blob/b69ab9f3ec7c3479d1c2a6829a67fa4198f5746a/src/charitygraph/phase5_execution_packet.py) is one of the more defensible parts of the implementation.

It:

- opens catalogue metadata read-only for packet construction;
- validates source-record and locator relationships;
- materializes retained content;
- checks content hashes;
- checks artefact identities;
- binds evidence units to task packets;
- requires locators for Discovery and Direct Service;
- renders prompts from governed packet material.

Source-record-backed evidence locators are supported without requiring every retained payload to have an `artifact_index` entry. That is a good distinction between source lineage and artefact indexing.

The main residual risk is representation completeness. PDFs, HTML and structured records have different extraction paths. A retained artefact can exist while its model-usable representation remains incomplete or ambiguous.

## 11. AI and LLM architecture

The project uses a sensible division of labour:

```text
Python / deterministic code:
  identity, hashes, scopes, schema validation, persistence,
  evidence references, state transitions, accounting

Models:
  bounded semantic interpretation,
  extraction, classification, relationship interpretation

Humans:
  high-consequence ambiguity, governance, product priority,
  sufficiency and stopping
```

The [semantic contract registry](https://github.com/gregorycwhill/charitygraph/blob/b69ab9f3ec7c3479d1c2a6829a67fa4198f5746a/src/charitygraph/phase5_semantic_contracts.py) separates:

- semantic contract identity;
- prompt identity;
- semantic schema identity;
- provider-facing schema name;
- adapter identity;
- route class;
- reasoning policy;
- authority state.

That separation is correct.

The provider boundary also correctly distinguishes internal Batch/Flex/Standard delivery from the Responses API `service_tier`.

### Important weakness

The registry is currently in transition. The new Direct Service V1.2 contract candidate increased registry size, but an existing test still expects the previous count. More importantly, the full suite exposes a prompt-policy binding mismatch for Direct Service.

This indicates that the contract registry, task builders and tests are not yet being evolved atomically.

## 12. Provider boundary and execution safety

The provider boundary is unusually explicit.

The Standard transport:

- accepts pinned request bodies;
- hashes request bytes;
- limits concurrency;
- records send-started state;
- avoids automatic retries;
- distinguishes terminal, systemic and ambiguous failures;
- persists raw responses;
- supports terminal replay;
- refuses unauthorized service tiers;
- verifies model, reasoning, schema, metadata and output limits.

The Batch path separately validates:

- UTF-8;
- no BOM;
- no NUL bytes;
- LF-only JSONL;
- exact custom-ID sets;
- duplicate IDs;
- structured schema names;
- cost ceilings.

This is good engineering for paid semantic execution.

### Residual concern

The implementation is still strongly shaped by the current Codex/mandate workflow. That is acceptable during development, but production Factory execution should not depend on host-level approval conventions that are external to CharityGraph.

The durable project authorization model should be independently operable by a normal service or trusted local runner.

## 13. Experimental methodology

The project has run many bounded experiments and has learned useful lessons about:

- delivery modes;
- evidence representation;
- source-role contamination;
- semantic repeatability;
- provider accounting;
- request identity;
- Batch lifecycle;
- Direct Service output defects;
- evidence addressing.

The experimental discipline is generally good:

- freeze inputs;
- pin hashes;
- distinguish logical tasks and physical attempts;
- preserve failed historical events;
- prevent accidental retries;
- prohibit automatic promotion;
- replay terminal state without provider calls.

### Methodological weakness

Many experiments optimize operational validity before semantic utility is sufficiently measured.

The project has strong evidence that requests were:

- transmitted at most once;
- reconciled;
- parsed;
- hash-consistent;
- financially accounted.

It has weaker evidence that the resulting proposals are:

- materially correct;
- useful to target users;
- stable under independent review;
- complete enough for real decisions;
- superior to simpler source-linked browsing.

The next experiments should therefore contain explicit semantic acceptance criteria, not only transport and accounting criteria.

## 15. ChatGPT/Codex development methodology

The project documents a supervisory model in which:

- Greg is product owner;
- ChatGPT provides supervisory reasoning and review;
- Codex performs local implementation and deterministic runtime work;
- bounded provider execution requires explicit authority;
- publication and merge remain separate boundaries.

### Genuinely good practice

The following practices should survive regardless of AI tooling:

- explicit authority boundaries;
- immutable manifests;
- no silent retries;
- append-only historical records;
- provider-free replay;
- separate logical and physical identities;
- fail-closed validation;
- source and semantic lineage;
- no automatic promotion;
- human ownership of stopping and product decisions.

### Tool-specific accommodation

The following are primarily adaptations to the current development environment:

- frequent mandate hashes;
- host-sandbox restrictions;
- manual authorization text;
- Codex-specific continuation prompts;
- handoffs between supervisory and implementation agents;
- repeated checkpoint and session-resumption protocols.

These should not become the product's conceptual architecture.

The durable Factory should expose a simple, explicit execution API that can be run by:

- a trusted local operator;
- a CI-controlled environment;
- a future worker service;
- an auditable production scheduler.

## 16. Detailed code review findings

### Positive findings

1. **Fail-closed contract resolution**  
   `resolve_contract()` rejects unknown profiles, family mismatches, prompt-policy mismatches and schema-policy mismatches.

2. **Evidence packet materialization**  
   Packet construction verifies source and artefact lineage rather than trusting task metadata alone.

3. **Provider schema validation**  
   Structured-output names are checked against the provider-safe pattern before serialization.

4. **Transport separation**  
   Batch, Flex and Standard are distinct delivery concepts.

5. **Append-only correction handling**  
   Reservation corrections and parser interpretations preserve historical rows rather than rewriting them.

6. **Idempotent terminal replay**  
   Replayed terminal items do not issue another provider operation.

7. **Explicit response-envelope parsing**  
   Batch envelopes are separated from inner Responses bodies.

### Concrete concerns

1. **Full-suite contract regression**  
   Four tests fail at the pinned Builder snapshot.

2. **Registry/test drift**  
   The registry contains 14 contracts while a test expects 13.

3. **Prompt-policy mismatch**  
   Direct Service task fixtures and the production registry disagree about prompt-policy identity.

4. **Potential read-side filesystem side effects**  
   `SQLiteCatalog._connection()` creates parent directories with `mkdir(parents=True, exist_ok=True)`. This is undesirable for a method that may be used in forensic or read-only contexts, even though the execution-packet module separately uses a read-only SQLite URI.

5. **Factory rehearsal hardcodes synthetic economics**  
   The provider-free rehearsal uses synthetic tariffs and fixed token usage. This is appropriate for chaos testing but should be clearly isolated from production accounting code.

6. **Mixed historical and current architecture**  
   Legacy CauseBase compatibility remains in package, Viewer and data paths. That is understandable, but it increases cognitive load and migration risk.

7. **Single large operational package**  
   Acquisition, source handling, semantic contracts, providers, runtime persistence, projections and historical compatibility all remain in one Builder distribution.

## 18. Complexity and over-engineering

CharityGraph is not simply over-engineered. Much of the complexity is paying for real requirements:

- evidence lineage;
- correction history;
- source-role semantics;
- incomplete and unavailable states;
- paid-provider safety;
- reproducibility;
- append-only publication;
- no-resend accounting.

However, complexity is now beginning to compound.

Warning signs:

- many phase-specific modules;
- multiple historical contracts;
- provider-specific transport code in the main package;
- mandate and host-safety concepts mixed with product execution;
- repeated campaign-specific scripts;
- compatibility names and old public release conventions;
- test fixtures that encode evolving identity rules;
- large domain scope before a narrow public workflow is complete.

The correct response is not an immediate rewrite. It is boundary clarification and deletion of obsolete paths once evidence shows they are no longer needed.

## 20. Completion risks and barriers

The main barriers are:

1. **Test and contract drift**  
   The pinned Builder snapshot is not green.

2. **Semantic quality uncertainty**  
   Structural validity is stronger than usefulness evidence.

3. **Private-runtime dependence**  
   Critical claims cannot be independently reproduced from Git.

4. **Source coverage uncertainty**  
   Provenance-unresolved and unavailable cells are legitimate but material.

5. **Control-plane complexity**  
   More code is being added to manage execution than to demonstrate end-user value.

6. **Public-contract timing**  
   Publishing vNext too early would freeze unstable semantic and coverage assumptions.

7. **Cross-repository coordination**  
   Data, Viewer and Playbooks evolve through separate branches and documentation changes, with limited evidence of automated compatibility checks.

8. **Cost and operations**  
   Real semantic execution is financially and operationally bounded but still requires careful reservation, reconciliation and provider accounting.

9. **Scope expansion**  
   Adding more claim families before validating the core workflow could delay useful delivery.

## 21. Challenge points

### Challenge 1: Is the full-card ambition necessary?

Not initially. A strong programs/services/evidence/identity product would already provide meaningful value. Full-card coverage should be an eventual platform direction, not the acceptance criterion for early product-market validation.

### Challenge 2: Is every distinction needed in the public model?

No. The internal model can remain rich, but the public contract should expose only distinctions that users and downstream systems can reliably understand and use.

### Challenge 3: Does neutrality require so much machinery?

Some machinery is necessary, but neutrality comes primarily from:

- transparent evidence;
- visible source role;
- explicit uncertainty;
- contestable corrections;
- avoidance of universal scores;
- clear separation between source fact and interpretation.

It does not require every internal lifecycle state to appear in every public view.

### Challenge 4: Is model routing sufficiently evidenced?

The project has bounded evidence for route-by-difficulty as an experiment hypothesis. It does not establish universal Luna/Terra superiority or a permanent product policy.

### Challenge 5: Is the current Factory architecture too local?

Yes, for future scale. The current local SQLite/filesystem design is a valid bounded implementation, but production-scale operation will require stronger queueing, object storage, worker coordination, secret management and operational observability.

## 24. Recommendations

### A. Before further significant paid Phase-5 build

1. Make the pinned Builder snapshot fully green.
2. Resolve the Direct Service prompt-policy mismatch at the task-builder/registry boundary.
3. Update registry-count tests through an intentional contract-registry policy, not a blind number change.
4. Separate production-bound contracts from candidates with an explicit status test.
5. Define semantic acceptance metrics for Discovery and Direct Service before further expansion.
6. Build a small independently adjudicated evaluation set.
7. Ensure all private-runtime aggregate claims have reproducible manifest and report identities.
8. Keep build-phase Standard delivery as the default.
9. Remove or quarantine obsolete campaign scripts after migration.
10. Add a clean-room public validation command that does not require private runtime data.

### B. Before first serious public vNext release

1. Publish a stable vNext contract with a small number of well-defined public primitives.
2. Demonstrate end-to-end source-to-Viewer lineage on a representative cohort.
3. Publish coverage and missingness honestly.
4. Demonstrate correction intake and traceable acknowledgement.
5. Establish Data/Viewer compatibility checks in CI.
6. Document which semantic outputs are candidates, accepted assertions or merely observations.
7. Verify source rights, privacy and Indigenous governance constraints.
8. Provide a release manifest and machine-readable provenance contract.

### C. After initial release

1. Add larger-scale worker orchestration only when workload requires it.
2. Introduce object storage and queue services behind stable interfaces.
3. Add technical replication cohorts and adjudicated semantic benchmarks.
4. Build Playbooks from real user questions rather than hypothetical method breadth.
5. Add Viewer semantic search only after the underlying embeddings and classification releases are real and governed.
6. Measure whether analysts can complete useful tasks faster than with ordinary web research.

### D. Explicitly defer

- universal charity scores;
- recommendation logic;
- hosted model inference;
- full sector-wide semantic enrichment;
- broad taxonomy harvesting;
- real-time completeness claims;
- public API/MCP infrastructure before demand is demonstrated;
- additional provider-mode experimentation now that Batch is sufficiently proven;
- further architecture expansion that does not improve a user-visible critical path.

## 25. Alternative architecture

A simpler near-term architecture could be:

```text
Source registry
  → immutable acquisition records
  → content-addressed artefacts
  → source-native records
  → a small evidence graph
  → bounded semantic tasks
  → reviewed candidate observations
  → immutable release
  → static Viewer
```

The operational control plane could initially be reduced to:

- subjects and scopes;
- source records;
- artefacts;
- locators;
- task manifests;
- task attempts;
- result records;
- cost ledger;
- release manifests.

Mandates and provider execution policies could be implemented as a separate execution service rather than mixed into the core catalogue.

This would preserve most of the epistemic value while reducing phase-specific coupling.

The existing architecture should not be rewritten wholesale. Instead:

- freeze the stable domain contracts;
- isolate transport and authorization;
- retire obsolete scripts;
- make the public release path the primary integration test;
- move experimental features behind explicit modules.

## 26. Counterfactual simpler product

A simpler initial product could focus on:

1. Australian charity identity;
2. source-linked organisation records;
3. programs and services;
4. geography and beneficiary populations;
5. explicit coverage and missingness;
6. source-native evidence;
7. transparent search and comparison;
8. static JSON/Markdown distribution;
9. correction proposals;
10. one or two Playbooks.

This would still be differentiated and valuable.

It would defer:

- detailed fundraising mechanisms;
- broad workforce modelling;
- extensive relationship semantics;
- all taxonomies;
- advanced semantic similarity;
- full portfolio economics;
- high-dimensional agent infrastructure.

The current project should adopt this as the product-validation slice even if the internal model remains broader.

## 27. Final judgement

CharityGraph is not a superficial AI wrapper. It is a serious attempt to build an evidence-governed, open charity knowledge infrastructure with explicit boundaries around uncertainty, provenance, corrections and downstream use.

The architecture is directionally right. The source/evidence/knowledge/release distinctions are valuable. The provider execution controls are stronger than typical early AI projects. Viewer and Playbooks have appropriately restrained boundaries.

The project is nevertheless in an intermediate engineering state:

- the Builder snapshot is not test-green;
- semantic usefulness is less proven than transport integrity;
- private runtime evidence supports the current narrative but limits external verification;
- the implementation surface is expanding faster than the demonstrated public product value;
- the public vNext release is not ready.

The best next move is not a rewrite and not another large semantic campaign.

It is:

> Stabilise the existing contracts, make the Builder snapshot green, validate a narrow public programs/services/evidence workflow with independent semantic review, and use that evidence to decide which of the broader domains deserve continued investment.

If that discipline is maintained, CharityGraph has a credible path to becoming a useful neutral evidence layer for Australian charity intelligence. If not, it risks becoming an impressive execution-control system whose public value remains under-demonstrated.
